- 구현 방식: AI 코딩 도구와 협업해 요구사항을 코드, 테스트, 배포로 연결

## 1. 30초 요약

사회초년생에게 금융, 주거, 직장, 권리 정보는 흩어져 있고 용어가 어렵다. 검색해서 한 번 읽어도 실제 판단 순간에는 기억나지 않는다는 문제에서 출발했다.

Life Quiz는 외부 원문을 그대로 복제하지 않고, 출처 링크가 있는 Quick Read와 Deep Read, 상황형 퀴즈로 재구성한다. 사용자가 직접 담은 카드에는 FSRS를 적용해 다음 복습일을 계산한다. AI는 사용자 요청마다 자유롭게 콘텐츠를 만들지 않고, 검증된 원천을 배치로 편집하거나 저장 콘텐츠 안에서 답하는 역할로 제한했다.

2026.08.01 기준 공개 콘텐츠 617건, 12개 분야, 17개 릴리즈, 하루 4회 수집 구조를 운영하고 있다. 공개 콘텐츠는 617건 모두 출처 URL과 퀴즈가 있고, 615건은 4장 카드 규칙을 만족한다. 로직 테스트 32건과 데스크톱·모바일 E2E 22건을 통과했다.

다만 사용자 성과는 아직 검증 전이다. 원격 D1에는 익명 브라우저 식별자 3개, 일일 학습 세션 2개, 복습 1건만 있어 완료율·재방문율을 성과로 주장할 수 없다. 또한 8월 1일 오늘 피드는 9건·3개 분야에 그쳐 목표인 12개 분야 최소 1건을 달성하지 못했다. 이 프로젝트의 다음 단계는 기능 추가보다 활성화 측정과 공급 다양성 SLO 검증이다.

## 2. 문제 정의

### 관찰

- 공공기관, 뉴스, 영상, 커뮤니티에 정보가 흩어져 있어 출처와 맥락을 함께 확인하기 어렵다.
- 전월세, 금리, ETF, 근로계약처럼 중요한 개념은 초보자에게 낯설고 한 번 읽고 지나치기 쉽다.
- 생성형 AI로 설명을 늘리면 비용과 환각 위험이 방문자 수와 함께 커질 수 있다.

### 문제 문장

사회초년생은 생활 의사결정에 필요한 정보를 찾더라도, 출처를 신뢰하고 자신의 말로 이해한 뒤 필요한 순간에 다시 떠올리기 어렵다.

### 검증 상태

초기 문제는 타깃 사용자의 일반적인 어려움과 기획자의 관찰로 정의했다. 정식 인터뷰나 행동 데이터로 검증한 단계는 아니다. 따라서 현재 문서는 사용자 니즈를 확정 사실로 쓰지 않고 제품 가설로 다룬다.

## 3. 핵심 가설과 성공 기준

### 핵심 가설

출처가 확인된 정보를 짧은 요약, 깊은 설명, 상황형 퀴즈, 간격 반복으로 연결하면 단순 피드보다 이해와 회상을 돕고 다시 방문할 이유를 만들 수 있다.

### 출시 전 성공 기준

1. 모든 공개 콘텐츠에서 실제 원문 링크를 확인할 수 있다.
2. Quick Read의 핵심이 Deep Read에 포함되고 네 카드가 서로 다른 역할을 맡는다.
3. 오늘의 5분 학습은 새 상식과 복습을 합쳐 5개 항목으로 안정적으로 유지된다.
4. 사용자의 응답에 따라 FSRS가 다음 복습일을 계산한다.
5. 콘텐츠 생성은 Cloudflare와 Gemini 무료 범위 안에서 운영된다.

### 사용자 성과 기준

- 첫 방문자의 5분 학습 시작률
- 시작한 사용자의 5개 항목 완료율
- 7일 안에 다시 복습한 사용자 비율
- 같은 문제를 다시 봤을 때의 정답률 변화
- 출처 확인, 이해 어려움, 중복 제보 비율

현재 사용자 성과 기준은 계측 정의만 완료됐고 표본은 충분하지 않다.

## 4. 우선순위와 트레이드오프

### 먼저 만든 것

- P0: 출처 링크, 공개·숨김 검수, 중복 차단
- P0: Quick Read, Deep Read, 상황형 퀴즈, FSRS 복습
- P0: 수집 로그, 분야 최소·상한, Gemini 예산
- P1: 오늘의 5분 학습, 관심 분야, 저장한 상식, 학습 리포트
- P1: 저장 콘텐츠를 근거로 답하는 라이프 메이트
- P1: 운영자 QA 대시보드와 수동 수집·검증

### 뒤로 미룬 것

- 정식 로그인과 기기 간 동기화: 익명 흐름의 사용성이 먼저 검증돼야 한다.
- 사용자 요청 시 실시간 콘텐츠 생성: 비용과 근거 품질이 사용량에 비례해 흔들린다.
- 종목 추천과 개인화 투자 조언: 교육 목적과 안전 원칙을 벗어난다.
- AI 이미지 생성: 무료 운영과 일관된 품질보다 우선순위가 낮다.
- 독립 Cron 추가: 같은 Cloudflare 계정의 Trigger 한도를 아끼기 위해 한 표현식 안에서 작업을 분배한다.

## 5. Case 1 - 서비스 구조를 기능이 아니라 원칙에서 결정

### 문제

프론트, 백엔드, DB, 예약 작업, AI를 각각 운영하면 초기 서비스에 계정과 비용, 배포 지점이 빠르게 늘어난다. 동시에 Gemini 키와 수집 API를 공개 앱에서 안전하게 분리해야 했다.

### 가설

Cloudflare Workers와 D1 안에 화면, API, DB, Cron을 모으고 비밀값이 있는 수집 Worker만 분리하면 무료 범위와 보안을 함께 지킬 수 있다.

### 핵심 PRD

1. `life-quiz` Worker가 Astro 화면과 사용자 API를 제공한다.
2. `life-quiz-ingest` Worker가 Hono, Cron, Gemini, 외부 API를 담당한다.
3. 두 Worker는 공개 URL이 아니라 Cloudflare Service Binding으로만 통신한다.

### 출시 판단

하루 네 번을 네 개 Cron으로 등록하지 않고 `0 3/6 * * *` 한 표현식으로 통합했다. Gemini는 12 RPM, KST 하루 400회, 회차당 최대 12번 생성 시도로 제한했다. 출처를 읽지 못한 항목은 추정 생성하지 않고 실패 로그에 남긴다.

### 결과와 학습

- 36개 커밋과 17개 릴리즈를 하나의 공개 저장소에서 운영했다.
- D1 크기는 약 4.0MB이고 공개 콘텐츠 617건을 저장했다.
- 배포 지점은 앱 Worker와 비공개 수집 Worker 두 개로 유지했다.
- 무료 여부만으로 기술을 고르면 관측성이 빠질 수 있다. 이후 `ingestion_runs`, Gemini 요청 로그, 운영 대시보드를 추가해 비용 제약을 제품 정책으로 바꿨다.

## 6. Case 2 - 읽기 피드를 5분 학습으로 바꾸기

### 문제

카드뉴스를 읽는 것만으로는 장기 기억을 확인할 수 없다. 모든 글을 자동으로 복습에 넣으면 큐가 과도하게 커지고 사용자의 의도도 반영되지 않는다.

### 가설

사용자가 직접 담은 카드만 복습 대상으로 삼고, 매일 복습 최대 2장과 서로 다른 분야의 새 상식을 합쳐 5개로 제공하면 부담을 낮추면서 회상 행동을 만들 수 있다.

### 핵심 PRD

1. 오늘 세션은 날짜와 브라우저별로 고정하고 새로고침 뒤에도 순서와 진행률을 유지한다.
2. 복습 최대 2개와 새 상식을 합쳐 총 5개로 만들고, 새 상식은 분야 중복을 최소화한다.
3. Again, Hard, Good, Easy 응답을 FSRS에 전달해 다음 복습일을 저장한다.

### 출시 과정의 판단

정식 로그인보다 익명 브라우저 식별자를 먼저 사용했다. 채택 신호가 없는 상태에서 인증과 계정 귀속을 먼저 만들면 개발 범위만 커질 수 있기 때문이다. 관심 분야는 최대 5개로 제한하고, 선호 주제를 우선하되 세션의 분야 다양성은 유지했다.

### 결과와 학습

- 5개 세션 고정, 선호 분야 우선, 연속 학습 계산을 로직 테스트로 검증했다.
- 데스크톱과 모바일에서 세션 생성, 진행 저장, 복습 흐름을 E2E로 검증했다.
- 원격 운영 데이터에는 일일 세션 2개, 완료 항목 0개만 있어 학습 효과와 완료율은 아직 판단할 수 없다.
- 다음 검증은 5명의 과업 테스트와 `방문 -> 시작 -> 첫 정답 -> 5개 완료 -> 7일 재방문` 퍼널 계측이다.

## 7. Case 3 - 수집 성공과 콘텐츠 건강을 분리해 보기

### 문제 신호

- 수집량이 하루 3건까지 떨어진 적이 있다.
- 2026.08.01 기준 오늘 피드는 9건이지만 주거 6건, 금융 2건, 투자 1건으로 3/12개 분야에 그쳤다.
- 최근 15일 발행량은 3-24건, 분야 수는 2-11개로 변동했다.
- 누적 공개 콘텐츠에서 부동산은 264/617건으로 약 42.8%를 차지한다.

### 원인

- Wikimedia 조회의 403·429와 YouTube 빈 응답이 일반 상식 공급을 끊었다.
- URL만으로 중복을 판단해 갱신된 공공데이터도 영구 중복으로 처리했다.
- Cron 실행이 성공으로 끝나도 후보가 비어 있는 수집원은 건강한 것으로 보였다.
- 서울 자치구 매매·전월세·생활정보를 각각 발행해 주거 카드가 피드를 점유했다.

### 가설

수집원별 후보·빈 응답·오류를 기록하고, 당일 부족 분야를 먼저 처리하며, 실패한 분야를 다음 회차에 다시 시도하면 무료 요청 한도 안에서도 다양성을 회복할 수 있다.

### 핵심 PRD

1. `ingestion_runs`에 수집원 진단, 생성·중복·지연·실패 항목을 저장한다.
2. 12개 분야에 일일 최소 1건과 상한을 두고 부족 분야부터 처리한다.
3. 실패한 출처형 상식은 같은 날 다음 회차에서 다시 후보에 넣고, 성공한 항목은 외부 조회 전에 제외한다.

### 출시 결과

- 원인 확인에 필요한 수집 로그, Gemini 예산, 최근 7일 소스 건강 상태와 수동 복구 UI를 출시했다.
- 동일 공공데이터는 응답 지문으로 중복 판정하고 자치구는 네 곳 비교 브리핑으로 통합했다.
- 12개 카테고리와 발행 최소·상한 정책을 코드와 테스트로 고정했다.
- 그러나 8월 1일 실제 결과는 여전히 3/12개 분야다. “자동 복구 기능 출시”와 “다양성 목표 달성”을 분리해 보고해야 한다.

### 학습과 다음 행동

Cron 성공률은 콘텐츠 건강 지표가 아니다. 최종 18시 회차 이후 `분야 커버리지 >= 10/12`, `일일 발행 >= 12`, `단일 분야 점유율 <= 35%`를 운영 SLO로 두고, 실패가 이어지는 분야마다 두 번째 독립 출처를 확보해야 한다.

## 8. QA와 협업 방식

### 품질 구조

- 로직 테스트 32건: 카드 중복, Deep Read 포함 관계, 25개 자치구 순환, 발행 상한, FSRS 세션, Gemini 예산, 소스 건강 상태
- E2E 22건: 11개 사용자 흐름을 데스크톱과 모바일에서 반복
- 타입 검사와 프로덕션 빌드
- 원격 D1 품질 쿼리와 운영자 대시보드
- 사용자 피드백 종류: 도움됨, 이해 어려움, 중복, 오래된 정보, 출처 문제, 퀴즈 문제

### 내가 맡은 판단

- 서비스 문제 정의와 대상 사용자 범위
- 정보구조, 12개 분야, 시작 코스와 5분 학습 흐름
- 출처·저작권·투자 안전·AI 생성 품질 정책
- 무료 운영 제약을 반영한 Cron, Gemini, D1 예산
- 오류를 재현하고 원인을 나누는 QA 기준과 릴리즈 우선순위

### 구현 협업

AI 코딩 도구를 활용해 요구사항을 코드로 옮기고, 생성 결과를 그대로 채택하지 않고 저장소 패턴, 타입 검사, 테스트, 원격 운영 데이터로 검증했다. 전통적인 개발·디자인 조직과의 협업 경험으로 과장하지 않고, 기획자가 구현 가능한 수준까지 제품을 이끈 개인 프로젝트로 설명한다.

## 9. 결과를 말하는 방식

### 말할 수 있는 결과

- 2026.08.01 기준 공개 콘텐츠 617건, 12개 분야, 17개 릴리즈
- 공개 콘텐츠 617건 모두 출처 URL과 퀴즈 보유
- 617건 중 615건이 4장 카드 규칙 충족
- 로직 32건, 데스크톱·모바일 E2E 22건 통과
- 하루 네 번 수집을 Cron 표현식 하나로 통합

### 아직 말할 수 없는 결과

- 사용자 수 증가, 재방문율, 학습 완료율 개선
- FSRS가 실제 장기 기억을 높였다는 인과 효과
- 챗봇이 문의 시간을 줄였다는 효과
- 12개 분야 일일 균형 달성

### 1주차 - 계측

- 홈 노출, 5분 학습 시작, 첫 응답, 완료, 복습 재방문 이벤트 정의
- 테스트 데이터와 실제 사용자 데이터를 구분하는 운영 태그 추가

### 2주차 - 과업 테스트

- 사회초년생 5명에게 `오늘 상식 찾기 -> 출처 확인 -> 5분 학습 -> 다시 복습` 과업 수행
- 이해하기 어려운 문장, 이탈 지점, 출처 신뢰 이유를 기록

### 3주차 - 콘텐츠 공급 SLO

- 18시 이후 분야 커버리지, 단일 분야 점유율, 수집원 빈 응답률을 일별 기록
- 실패가 반복되는 분야에 독립 출처 두 번째 경로 추가

### 4주차 - 다음 투자 판단

- 5분 학습 완료율과 7일 재방문 신호가 확인되면 로그인·기기 동기화 진행
- 신호가 없으면 인증보다 첫 세션 길이, 문제 난이도, 홈 진입점을 먼저 수정
